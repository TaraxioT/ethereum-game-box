The game store and the AI verifier

The plan for games that live online instead of on the Box. A team-published zip holds a game's page and the rules an AI judge follows. The Box downloads the game each time it runs, up to four players stake and play, and an agent on 0G's private inference reads the match's log and says who gets paid how much. If it can't, everyone gets their stake back. Built and tested on the branch game-store, on fakes and two seats: nothing is deployed, 0G hasn't judged a real match, it hasn't run on the Pi, and step 7, four seats on the Box, isn't done. pnpm store:e2e plays it end to end on one laptop: anvil, the real Workers on wrangler dev, a real container and the real Box in a real browser, with only 0G and the badges faked.

01Goal

  • A mini game store: an online index of every game bundle. There are no updates: a Box downloads a game each time it runs.
  • A game bundle: a zip holding index.html, the game, and manifest.json, which describes it and carries the AI verifier's instructions.
  • A game verifier: a Docker container, started on demand, that runs an agent over the match's logs and the manifest's instructions. It ends with who gets paid how much. On any failure, the funds go back to the addresses they came from.

Not in this plan: an in-Box store page, a store page on the public site, Forge-built games in the store, titles or stats for store games, and any game fee.

03What this does and doesn't prove

Say this plainly on the site and in the demo.

  • 0G proves an enclave handled each turn. In Private mode each turn runs in an attested enclave. Mainnet's replies carry no tee_verified field, so the Worker checks each turn itself: the enclave's signature for that chat must recover to the key 0G's serving contract lists for the provider. It refuses any reply that fails. Say "each turn passed an attested enclave".
  • 0G doesn't prove the prompt or the reply. The signed text is two hashes of ciphertext, which nobody outside the enclave can recompute, so the signature binds neither the prompt nor the reply's text to that chat. No contract can check that a verdict came from the real log.
  • The Worker and the container aren't enclaves. Whoever runs them could feed the agent a false log or sign a false verdict. The verifier key is trusted, and the contract limits the damage: it pays only the players the Box named, and only the exact pot.
  • The pot's admin is trusted as far as the verifier key. It can replace that key, so it could make itself a verifier. It is its own account, and the deploy takes the role away from the relayer's key. That key still licenses Boxes until the admin hand-over, so a leak of it could forge a log, but not sign a verdict.
  • The Box is trusted for taps and for who plays. It records the taps and signs the log, so a dishonest Box could forge one. It also names the players, and a badge signs nothing. So a dishonest Box could name a badge that never tapped, stake its whole balance and forge a log that pays the Box's own badge. It could also keep a balance locked, by opening a new pot each time one is refunded. open has no cap on a stake, and one wouldn't help: a Box can open pot after pot. DuelPot trusts a Box the same way. This is fine for a token with no value, when only the team licenses a Box and can suspend one. Real money would need the badges to sign.
  • A store game isn't Verified. That tier means the chain checks the result. Store games get a new tier, judged, shown on Stake before anyone stakes.

05One match, end to end

  1. Pick. The rack shows store games from the index. If the index can't be reached, they don't appear, and team games play as usual.
  2. Join. Two to four badges tap in, as many as the manifest allows.
  3. Download. The Box fetches the zip into a temporary folder and checks its hash and shape. If that fails, the game is sealed and nothing is staked.
  4. Stake. The Box signs a Stake naming the bundle's hash, the players and the amount. StorePot pulls Store USDC from each player.
  5. Play. The game runs in the sandboxed frame. The Box records every tap and every event the game posts.
  6. End. The game says it's over, or the manifest's time limit runs out. The Box signs the log and sends it to the verifier. The screen shows JUDGING.
  7. Judge. The Worker checks the Box's signature and that the pot is open, and takes the instructions from the store by hash, never from the Box. It starts a container, and the agent works until it submits a verdict.
  8. Pay. The Worker checks the verdict, builds the audit record, puts its hash in the signed verdict and sends it through the relayer. StorePot pays each player their share. The Box shows the split.
  9. Keep. The Worker uploads the record to 0G Storage, and retries until it lands. The Box deletes the bundle.

On failure: one retry on a fresh container. If that fails too, the Worker signs a refund and each stake goes back to the address it came from. If the verifier never answers at all, anyone can call the refund after a delay, and the Box's sweep does so.

A failure is any of: a timeout, 0G unreachable, a reply that fails the TEE check, an agent that says it can't judge, or a verdict that fails the Worker's checks.

06The bundle

A zip of index.html, manifest.json and any assets the page uses by relative path.

{
  "format": 1,
  "id": "tap-rush",
  "title": "Tap Rush",
  "blurb": "Most taps in ten seconds takes the pot.",
  "players": { "min": 2, "max": 4 },
  "minutes": 1,
  "stakes": [5, 10, 25],
  "taps": "identify",
  "verifier": {
    "instructions": "Count each player's accepted taps from the Box's log. Most taps wins the whole pot. On a tie, split it evenly between the tied players."
  }
}
  • Checks on upload and on download: the same reader, which refuses unsafe paths, oversized files and zip tricks. It starts from the .game prototype's reader, which was tested against hostile zips.
  • The hash is the game's identity. It is the sha256 of the zip. The store never lets a listing change.
  • A bundle's code is untrusted. It runs only in the kiosk's sandboxed frame, under the Box's own CSP header with no network, and never in Node.

The game's powers

A small script the Box adds to the frame gives the game one object:

  • In: the players and each tap (seat, time and roll, when the game asks for rolls).
  • Out: event(name, data) for the log, station(seat, text) and buzz(seat), cut to what a station shows and rate limited, and end().

A game has no say over money. Its end() only closes the match.

07The store

  • GET /index.json: every listing: id, title, blurb, players, stakes, icon, hash and size.
  • GET /bundles/<hash>.zip: a zip, cached forever.
  • POST /bundles: an upload with the team's token. It runs the reader, stores the zip and adds the listing.
  • pnpm store:publish <folder>: zips a folder, uploads it and calls StorePot's list(hash).

An unlisted hash can't be staked: StorePot checks that the team listed it, so a Box can't stake on a game the team never read.

08The verifier

The Worker is the only part with secrets: the verifier key, the 0G API key and the 0G Storage wallet.

The container has no secrets and no internet. enableInternet = false, and its one way out is a Cloudflare outbound handler back to the Worker. It starts on demand, one per match, and stops at the end.

The agent is our own small loop on the OpenAI format, with two tools: shell and submit_verdict. It gets the instructions and the log as files. It must end with submit_verdict, either as a split or as cannot_judge. Limits on turns and time end a run that wanders.

Every model call goes through the Worker's proxy, which sets X-0G-Provider-Trust-Mode: private and verify_tee: true, and fails the run on anything else. It records each turn, with its chat ID.

Text from a game can steer the agent. The log's game events are labelled as claims, and the prompt says to treat them as data. That helps but doesn't guarantee anything, so the design assumes a tricked agent. The most it can do is propose a bad split between the match's players, or fail the run. The team reads each game before listing it.

The audit record holds the log, the instructions, every turn with its chat ID, and the verdict. Its hash goes on chain with the verdict.

09The contract

StorePot takes up to four players, and is separate from DuelPot and BoxResults.

Call Signed by What it does
list(hash) The lister key Lets a bundle be staked.
open(stake) The Box's P-256 key Pulls amount from each player into a pot, keyed by Box and round.
settle(verdict) The verifier key Pays payouts[i] to players[i]. Refuses unless the payouts add up to the pot.
void(refund) The verifier key Sends each stake back at once.
refund(box, round) Nobody The same, for anyone, after the delay.

A verdict names players only by position, so it has no way to pay anyone else. It also carries the audit record's hash.

10Four players

The Box assumes two players throughout: Seat is 0 | 1, ports use pairs, EGB_STATIONS must be exactly two, and Join, Stake and Result draw two sides. This pass widens all of it to four.

  • Team games stay two-player. Their rules use other(seat), and a game's manifest sets its own limits.
  • The firmware already takes four stations (MAX_STATIONS).
  • Refunds and results pay a list of players, not a pair.

11Steps

Each step ends with tests, and step 1 can stop the plan.

  1. Prove 0G. On mainnet: is there a private model, do tool calls work, and does verify_tee come back? Does the 0G Storage SDK run in a Worker? Done: tool calls work, tee_verified doesn't come back so the Worker checks the enclave's signature itself, and the SDK runs in the Worker with a fetch transport, so no second container.
  2. The bundle. The format, the reader and a sample game, Tap Rush.
  3. The store. The Worker, R2, store:publish and a deploy.
  4. The contract. StorePot, its forge tests, Store USDC, the deploy and the relayer's routes.
  5. The verifier. The Worker, the container, the agent and the failure paths, against a fake 0G.
  6. The Box, two seats. The library, the frame's powers, the log and the chain. A full staked match on the Pi.
  7. Four seats. The core, the settings, the stations and every screen.
  8. Mainnet 0G. Deploy with the real key and play one match.

12Build detail

Steps 2 to 4 need no 0G key. Step 2 comes first, then steps 3 and 4 can run side by side. Step 1 runs as soon as a key arrives, and steps 5 to 7 get their detail from its results.

Step 2: the bundle

  • Where: packages/sdk/src/bundle/, a new entry @egb/sdk/bundle. It runs unchanged on the Box, in a Worker and in a browser.
  • read.ts starts from the .game prototype's reader, in worktree wf_1c26fd3f-9a5-1. It accepts one exact zip shape and refuses everything else.
  • pack.ts is the only way to make that shape: sorted names, fixed fields and no timestamps. So store:publish takes a folder, not a zip, and the same folder always gives the same hash. A zip made by another tool is refused.
  • format.ts holds the manifest's type, its checks and the limits: 16 MB a zip, 64 files, and .html, .css, .js, .png, .jpg, .webp, .svg, .woff2 and .mp3 only.
  • Tap Rush is the sample, in apps/store/sample/tap-rush/, with instructions a test can check by hand.
  • Tests: the prototype's hostile zips (unsafe paths, overlaps, zip bombs), a changed byte, and packing twice to one hash.

Step 3: the store

  • Where: apps/store, a Worker named gamebox-store, with an R2 bucket gamebox-bundles, on the relayer's Cloudflare account. Containers and R2 both work on that account.
  • Storage: bundles/<hash>.zip and listings/<hash>.json, written only if absent, so nothing can be overwritten. /index.json is built from the listings.
  • Uploads: POST /bundles needs the secret STORE_PUBLISH_TOKEN. It runs the reader, recomputes the hash and refuses an id already taken by another hash. A new version needs a new id, such as tap-rush-2.
  • Reads: open to anyone. A zip is sent with cache-control: immutable.
  • pnpm store:publish <folder>: packs, uploads and prints the hash. It calls list(hash) once step 4 is deployed.
  • Tests: every refusal against an in-memory R2, then a publish and a download from the live Worker.

Step 4: the contract

  • StorePot, in contracts/src/game/, with its own EIP-712 domain, Game Box Store Pots v1, and BoxCheck for the Box's signature.
  • Messages:
    • Stake(string box, bytes32 bundle, uint256 round, address[] players, uint256 amount, uint256 deadline)
    • Verdict(string box, uint256 round, uint256[] payouts, bytes32 record, uint256 deadline)
    • Void(string box, uint256 round, bytes32 record, uint256 deadline)
  • Roles: LISTER_ROLE lists bundles. A verdict's signer must hold VERIFIER_ROLE, so an admin can replace the key. The admin is its own account, apart from the relayer and the verifier key.
  • It refuses: an unlisted bundle, fewer than 2 or more than 4 players, a repeated player, a pot that exists, payouts of the wrong length or sum, a pot that isn't open, an expired deadline, and a wrong signer.
  • Deploy: FakeUSDC again as StoreUSDC, with the relayer as minter, then StorePot, then setGameSpender, and the pot's admin role goes from the deployer to STORE_ADMIN. The deployer needs Sepolia ETH and sends with --skip-simulation -g 150, like the other scripts.
  • Shared: digests, ABIs and test vectors in packages/shared/src/store/.
  • Relayer routes: /store/open, /store/settle, /store/void, /store/refund and /store/topup, each in the existing checked-then-sent pattern.
  • Tests: forge tests for each refusal, every payout shape from 2 to 4 players, and settle racing the refund; vectors shared with TypeScript; and a test for every relayer refusal.

Noted for step 6

  • FromFrame accepts only ready and error today. It gains event, station, buzz and end, each capped.
  • Game events reach the server through the kiosk, so they need a new ScreenCommand.
  • frameCsp has no inline scripts, and an index.html will want them. A bundle gets its own policy, which still has connect-src 'none' and the sandbox.
  • GameInfo.kind gains store, and Stake's tier plate gains judged.

14Still to confirm

These came up while writing the plan. Each has a default the build will use unless the team says otherwise.

  • Team games: they stay two-player. "2 to 4, everywhere" means the Box and store games.
  • The tier's name: judged.
  • Who pays for 0G: the team, from one balance. Players pay nothing extra, and a Box can't run up the bill beyond one run per open pot.
  • The one-chain rule: CLAUDE.md says not to add other chains. 0G Storage needs transactions on 0G's chain, so the rule gets one exception: storage payments only, and no contracts there.
  • The refund delay: one hour, as DuelPot.
  • Player names: StorePot doesn't need them, but the Box's stake flow keeps asking for one, as it does today.
  • Icons: store cartridges use the fallback icon in this pass.
  • Bet on X and B17: unchanged by this plan.

15Done when

  • A team member publishes a game, and it appears in the rack on the Pi.
  • A changed zip is refused, and an unlisted hash can't be staked.
  • Four real badges on four stations stake and play a store game on the Pi.
  • The agent's verdict pays a split on Sepolia, and the Box shows it.
  • Killing the verifier mid-run retries once, then refunds each stake to its address.
  • A forged verdict, one that doesn't add up, and one from a wrong key are all refused.
  • With the verifier down, the refund works after the delay.
  • Every model turn passes the TEE check, on mainnet 0G.
  • The audit record is on 0G Storage, and its hash matches the chain.
  • The container has no secrets and can't reach the internet, proved by a test run from its shell.
  • pnpm typecheck, the tests and pnpm contracts:test pass.
